## How the API signatures were verified

Read every non-test `.go` file at the repository root before writing a word of the skill:
`alg.go`, `blocklist.go`, `claims.go`, `classify.go`, `doc.go`, `ecdsa.go`, `eddsa.go`,
`enrich.go`, `expected.go`, `extract.go`, `gcm.go`, `hmac.go`, `jwk.go`, `jwk_aws_cognito.go`,
`jwt.go`, `keyset.go`, `kid_keys.go`, `leeway.go`, `none.go`, `pair.go`, `required.go`, `rsa.go`,
`rsapss.go`, `sign.go`, `signoptions.go`, `token.go`, `token_jwe.go`, `tokenpair.go`, `util.go`,
`util_safe.go`, `validators.go`, `verify.go`. Also read the README, `_examples/*/main.go`, and
`go.mod`.

After drafting, cross-checked completeness with `go doc -all .`, listing all 181 exported
declarations and diffing them against what the reference documents cover. That pass caught one
real gap: `keyset.go` (the self-refreshing `KeySet`/`NewRemoteKeySet`/`NewCognitoKeySet` API)
had been missed on the first read-through. It is now documented in `api-map.md`,
`keys-and-jwks.md`, `security.md` and `testing.md`.

`go build ./...` and `go vet ./...` both pass; no `.go` file was touched.

## Concerns

- **doc.go and the README's own doc comments are not fully trustworthy**, and this is called out
  explicitly in `SKILL.md` and `testing.md`: `doc.go`'s embedded example writes
  `jwt.Claims{ExpiresAt: ...}`, but the actual field is `Expiry` (`ExpiresAt()` is a method, not
  a field) — that struct literal does not compile. The same file's `jwt.Verify(jwt.RS256, keys,
  token)` example passes a `Keys` map where `Verify` expects a `*rsa.PublicKey`, which would fail
  at runtime with `ErrInvalidKey`. Neither example is compiled by CI (the package has no `func
  Example*` tests), so nothing catches this. I did not fix `doc.go` itself (out of scope, and the
  task was to write a skill, not patch the library), but every reference document is written
  from the real source, not from these comments, and the skill says so.
- **The jwt working tree already had a large amount of unrelated, pre-existing staged (but
  uncommitted) work when I started**: a source-level refactor across most `.go` files plus a
  `brand/` logo/asset addition already touching `README.md`, tracked by `COMMIT-PLAN.md` and
  `PASS-LEDGER.md` in the repo root. This predates my session and is not something I created or
  modified. My `git add` only added the new skill/plugin files and my own `README.md` hunk to
  that already-staged index; nothing pre-existing was touched, unstaged, or committed. Worth
  flagging so it is not mistaken for something this task introduced.
- The marketplace name `kataras-jwt` and the plugin's missing `version` field both mirror pg's
  choices exactly, on the assumption that consistency across the author's plugins is desired.
