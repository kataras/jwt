# jwt brand kit

The mark is a key. Its three teeth are the three dot-separated segments of a JWT, and the
last one is gold because the last segment is the signature. The hole in the bow is gold for
the same reason: it is the part that has to match.

Everything here is generated by `main.go`. Nothing in this directory is edited by hand.

```sh
cd brand && go run .
```

That writes the SVGs into this directory and the PNGs into `export/`. It needs a
Chromium-family browser to make the PNGs; without one it writes the SVGs, says so, and
exits zero, so a checkout with no browser still regenerates the vector art. Add `-svg-only`
to skip the PNGs deliberately.

## Palette

A sibling of the Iris kit rather than a copy. The gold is carried over unchanged, because
that is what makes the two projects look related. The blue moves from Iris indigo to
Aegean, so the two marks are never mistaken for each other at a glance.

| | Hex | Where |
| --- | --- | --- |
| Aegean | `#0D5EAF` | The key, on light grounds. |
| Sky | `#4E9BE0` | The key, on dark grounds. Aegean sinks into the dark field. |
| Deep | `#08406F` | Depth. Unused by the mark itself; kept for the kit. |
| Gold | `#F5C542` | The bit of the key and the hole in the bow. Shared with Iris, unchanged. |
| Marble | `#F4F1EA` | Warm off-white ground, and the wordmark on dark. |
| Field | `#0A0E1F` | The dark ground. Shared with Iris. |

The library itself has no stylesheet and no tokens, so there was nothing here to reconcile
against. These values were chosen against the Iris kit at `C:/github/iris-book/brand`.

## The two cuts, and where the boundary sits

**The boundary is 48 pixels**, set by `smallCutBelow` in `export.go`. At 48 and above the
full mark is exported; below it, the small cut.

The small cut is not the mark scaled down:

- **Two teeth instead of three.** Below 48 px the gap between three teeth lands inside one
  pixel and they merge into a single wedge.
- **Heavier strokes**, but only for the teeth and the shaft.
- **A larger ring with a thinner stroke and a smaller hole.** This is the counterintuitive
  part and it is the one that decides whether the mark survives. What has to be protected
  is the light gap between the hole and the ring. At 16 px that gap was about one pixel
  wide, went sub-pixel under antialiasing, and closed into a grey smear that took the whole
  bow with it. Widening the gap matters more than thickening the ink around it.

The boundary was chosen by rendering both cuts at 16, 24, 32 and 48, magnifying the raster
eight times, and looking. It is not a round number picked for tidiness.

`favicon.ico` carries three frames, 16, 32 and 48. The first two use the small cut and the
48 uses the full one, by the same rule, because `bodyForSize` decides for every export in
one place.

no font to load and nothing to fall back to.

## Clear space and minimum size

Clear space is the radius of the key's bow on every side, which is about one fifth of the
mark's width.

Minimum size is **16 px** using the small cut. Below that the bow's hole closes whatever
you do, and the mark stops being a key. For anything smaller, use a solid Aegean square
with a gold dot, or nothing.

## Inline safety

Every SVG here obeys these, and they are constraints rather than preferences:

- Flat colour only. No gradients, no filters.
- No `<defs>` and no ids. Ids collide when several of these land in one document, which is
  exactly what happens in a single-file HTML build.
- No `<style>` block, no CSS classes, no `var()`. Presentation attributes with hardcoded
  hex, nothing else, so the art does not inherit or leak styling.
- A `filter` is specifically fatal for the book: Chrome rasterizes a filtered subtree when
  printing to PDF, so a filtered mark silently stops being a vector at exactly the moment
  it matters most.

The only exception is `jwt-mark-mono.svg`, which uses `currentColor` on purpose so a single
ink context can drive it.

## The README header, and the float

`align="left"` on an `<img>` creates a CSS float, and Markdown has nothing that clears it.
Without a clear, a logo taller than the intro paragraph hangs past it and shoves the first
line of the next block sideways.

```html
<img align="left" width="72" height="72" src="brand/export/jwt-mark-256.png" alt="">

Zero-dependency, lightweight and fast JWT and JWKS implementation...

<br clear="left"/>
```

`<br clear="left"/>` survives GitHub's HTML sanitizer, which strips most attributes but
keeps this one.

The logo is 72 px. GitHub caps the README column at about 1012 px however wide the monitor
is, so the intro paragraph wraps to two lines there and the mark overhangs it by roughly 30
px, which the clear absorbs. Rendered at both a 900 px and an 1800 px container and looked
at: at 1800 px the paragraph does collapse to one line and the overhang grows, and the
clear still keeps the next block in place. That case does not occur on GitHub, but the
clear is there so that it does not matter if it ever does.

## Rebuilding

```sh
cd brand && go run .              # SVGs and PNGs
cd brand && go run . -svg-only    # SVGs only, no browser needed
```

To change the mark, edit `markBody` in `mark.go` and run the generator. Everything else,
the on-dark variant, the mono variant, the lockup, the hero and every PNG, is derived from
that one function, so there is no second copy to keep in step.

If you change the geometry, look at the result before committing it. Render both cuts at
16, 24, 32 and 48, magnify the raster, and extract the `.ico` frames rather than trusting
that the right cut landed in each. Three of the six candidate directions for this mark
looked fine as markup and fell apart the first time anybody rendered them.
